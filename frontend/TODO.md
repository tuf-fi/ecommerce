# Inventory Management — TODO

Status as of 2026-09-02. Already shipped (frontend-only pass): per-product
`reorderThreshold`, size-aware `productStockStatus()`, negative-input
clamping + duplicate-SKU guard in `ProductModal`, real timestamp + actor on
stock-log entries, and the dashboard "Expiring Soon" panel. Everything below
is still open.

## 1. Cart ↔ Inventory unification (do this before anything else here)

The customer store (`library/store.tsx`, static `PRODUCTS` from
`library/products.ts`) and the admin store (`library/adminStore.tsx`, derived
`ADMIN_PRODUCTS` from `library/admin/products.ts`) are two separate datasets
in two separate provider trees (`StoreProvider` at root layout, `AdminProvider`
only under `/admin`). Stock lives in both places independently and never
syncs. This is the root cause of the biggest gap: a customer can add
out-of-stock items to cart, and completing an order never touches product
stock.

- [ ] Pick one product/stock source of truth. Cheapest path: move
      `AdminProduct`-shaped data (with `stock`/`sizes[].stock`) to a single
      module both trees import, and delete the separate `Product` type in
      `library/products.ts` (it currently has no top-level `stock` field at
      all for non-sized products — that gap has to close first).
- [ ] Mount one shared provider (or have `StoreProvider` read from the same
      state `AdminProvider` uses) so a stock edit in `/admin/inventory` is
      visible to the storefront without a reload.
- [ ] `addToCart` (`library/store.tsx:87`) must check live stock and refuse
      (or cap) quantity beyond what's available — right now it only caps at
      `MAX_PER_ITEM = 6` regardless of actual stock.
- [ ] Decrement stock when an order is placed (or moves to "Paid" —
      decide the trigger) via `updateOrderStatus`
      (`library/adminStore.tsx:174`), and log it through the existing
      `logStock` audit trail with a distinct reason (see §3).
- [ ] Decide what happens to reserved stock on order cancellation
      (restock or not) and implement the same way.
- [ ] Note for later: once a real backend exists, this decrement needs to be
      atomic with order creation (DB transaction / conditional update) to
      prevent overselling under concurrent checkouts. Not fixable purely on
      the frontend — flag it in the backend TODO when that work starts.

## 2. Bulk operations & data model gaps

- [ ] CSV import for restocking (bulk stock updates) and CSV export of the
      current inventory table.
- [ ] Bulk actions on the inventory table (multi-select rows → bulk
      price/stock edit, bulk delete).
- [ ] Supplier fields on `AdminProduct` (supplier name, cost price, lead
      time) — currently nonexistent; needed for reorder decisions.
- [ ] Reason codes on stock-log entries. Right now `logStock` infers
      `in`/`out`/`adj` purely by diffing old vs. new stock in
      `updateProduct` (`library/adminStore.tsx:137-158`), so an edit that
      only fixes a typo but happens to also change stock gets miscategorized.
      Replace the diff-inference with explicit reasons passed by each
      call site (e.g. `"restock"`, `"correction"`, `"sold"`, `"removed"`,
      `"damaged"`).

- [ ] Real photo upload to Cloudinary. `ProductModal.handlePhotoChange`

- [ ] Real admin auth (JWT + httpOnly cookies, role check) — placeholder

- [ ] Optimistic locking / concurrency control on product edits (e.g. a

- [ ] Atomic stock decrement on order placement — see §1's last bullet.

## Design Specificity Verdict

**A bespoke tool, not a re-skinned admin template.** The navy/pink/gold discipline and hairline-border system from the brand rules carry into the admin surface; chart color choices are deliberately reasoned in-code (gold explicitly withheld from charts because "it belongs to star ratings only"); the `ContentEditorShell` + `LivePreviewPane` architecture — a live, device-width-togglable preview stacked above ten different content-editor forms — is a genuinely unusual pattern built specifically for a brand where "what will this look like on the real page" matters more than a typical SaaS admin. No shadcn-card-with-shadow pattern anywhere.

**Deterministic scan**: clean (`[]`) across all 8 admin targets — again, the detector's rule set (animation/typography/gradient patterns) doesn't cover the React-specific accessibility gaps found manually, so this result should not be read as "no anti-patterns present."

**Manual/code evidence layer**: this is where the real signal is. `htmlFor`/`id` label association exists in exactly **1 of 18 files** that contain a `<label>` (`ProductModal.tsx` — proving the correct pattern is known in this codebase, just not applied elsewhere: `LoginForm.tsx`, `StaffModal.tsx`, `HeroEditor.tsx`, and every other content editor/modal use visually-adjacent, unlinked labels). Every text input and select in the panel shares one `outline-none` focus treatment (`formClasses.ts`) with no real focus-visible ring — a single structural fix point, not scattered one-offs. Five separate table-row click targets (`staff`, `orders`, `inventory`, `FaqEditor`, `TestimonialsTab`) are mouse-only with `cursor-pointer` and no `role`/`tabIndex`/`onKeyDown`. Zero `scope=` attributes exist on any `<th>` across the entire admin surface. Icon-only buttons, by contrast, are consistently well-labeled (`aria-label` present sitewide), and status badges never rely on color alone — both genuine strengths, not gaps.

## Overall Impression

The visual craft and brand fidelity are real, and the live-preview CMS architecture is a standout. But the panel has one architecturally dishonest pattern (content editors that claim a draft/discard safety net they don't actually provide), one unguarded high-stakes action (order status changes), and a genuinely systemic, single-root-cause accessibility gap (focus indicators + label association) that touches nearly every screen. None of these require a redesign — they're concentrated in a handful of shared files.

## What's Working

1. **`StockHealthDonut.tsx`'s dual-modal control** — the pie itself is `aria-hidden` because its click target isn't keyboard-operable, and a real, tabbable button-based legend is the actual accessible control for the same filter action, documented in-code as a deliberate decision. Most dashboards skip this reasoning entirely.
2. **`ContentEditorShell` + `LivePreviewPane` architecture** — one shared shell drives ten distinct content editors, giving every one a real rendered preview and device-width toggle for free.
3. **Skeleton-loading parity** — nearly every list/detail page ships a skeleton that mirrors its real layout closely enough to avoid layout shift.

## Priority Issues

**[P0] Content editor "Save"/"Discard" is fiction for most single-entity editors**
- **Why it matters**: `library/content.tsx`'s shared state (`hero`, `about`, `philosophy`, `newsletter`, `contact`, `socialLinks`, `catalogue`, `pageIntros`) is mutated directly in each `onChange` handler across `HeroEditor.tsx`, `AboutEditor.tsx`, `PhilosophyEditor.tsx`, `NewsletterEditor.tsx`, `PageIntroEditor.tsx`, `CatalogueEditor.tsx`, `ContactTab.tsx`, and the Social Links block in `LinksTab.tsx` — content goes live on the actual customer-facing site the instant a key is pressed, not on Save. `ContentEditorShell.tsx`'s "Discard unsaved changes?" prompt navigates away without reverting anything. This directly contradicts how Blog/Promotions/Pages editors correctly work (local draft state, mutate only on Save), so an admin who learns "Discard is safe" on one tab is wrong on another.
- **Fix**: Route every listed editor through local draft state (mirroring `PageContentEditor.tsx`'s pattern) and only call the real `updateX()` setter inside `handleSave`.
- **Suggested command**: `/impeccable harden`

**[P1] No confirmation on order status changes**
- **Why it matters**: `components/admin/modals/OrderModal.tsx:32-42` fires `onStatusChange` the instant the status select changes — including transitions to Cancelled — with zero confirmation. This is the single highest-stakes, customer-visible action in the panel, and it currently has less protection than a low-stakes wishlist toggle gets on the customer site.
- **Fix**: Gate "→ Cancelled" (and optionally "→ Delivered") behind the same `ConfirmModal` pattern already used for every delete action in the app.
- **Suggested command**: `/impeccable harden`

**[P1] Staff deletion has no self-protection or last-admin guard**
- **Why it matters**: `library/adminStore.tsx:220-223` unconditionally deletes any staff id. Any signed-in account can delete the last remaining Administrator, or their own account mid-session, with only generic confirm copy — a concrete consequence of the still-open RBAC gap.
- **Fix**: Add two client-side guards ahead of full RBAC: block deleting your own logged-in account, and block deleting the last remaining Administrator.
- **Suggested command**: `/impeccable harden`

**[P1] Systemic accessibility gaps: unlabeled inputs, no focus indicator, mouse-only table rows**
- **Why it matters**: This is one root-cause problem with panel-wide reach. `htmlFor` association exists in only 1 of 18 files with form labels — every other form (login, Staff, Product, every content editor) has a label that's visually adjacent but not programmatically linked. Every text input/select shares one `outline-none` treatment with only a subtle border-color shift on focus (`formClasses.ts`) — no project-wide `:focus-visible` fallback exists. Five table-row click targets (Staff, Orders, Inventory, FaqEditor, TestimonialsTab) are `cursor-pointer` with no `role`, `tabIndex`, or `onKeyDown` — mouse-only. Zero `<th scope>` attributes exist anywhere. Together these block a keyboard-only or screen-reader admin (Sam) from reliably operating the panel at all, and make focus position hard to track for everyone tabbing through a form.
- **Fix**: Fix once at the shared root — add `htmlFor`/`id` pairs across the flagged forms, add a real focus-visible ring to `FIELD_INPUT`/`FILTER_SELECT` in `formClasses.ts`, convert the five clickable rows to real buttons or add `role="button"`/`tabIndex`/`onKeyDown`, add `scope="col"` to table headers.
- **Suggested command**: `/impeccable audit`

**[P2] No bulk actions or keyboard shortcuts anywhere in the panel**
- **Why it matters**: Heuristic 7 (Flexibility/Efficiency) scores 1/4 — the lowest score in either flow. Orders/Inventory/Staff have no row checkboxes, no "select all," no batch status/price/stock edit; Import/Export buttons are wired to nothing; there isn't a single keyboard shortcut in the panel, not even for "new product"/"new staff." For an internal Operate-mode tool run by staff processing many rows a day, this is real daily friction, not a nice-to-have.
- **Fix**: Add row checkboxes + a batch action bar to Orders/Inventory/Staff tables, and wire Import/Export to real functionality (or remove them until they exist).
- **Suggested command**: `/impeccable optimize`

## Persona Red Flags

**Alex (impatient power user)**: No global search/command palette — each page has its own isolated search box. No bulk actions confirmed by reading Orders/Inventory/Staff in full — every action is single-row only. Zero keyboard shortcuts, not even for "+ Add" actions. Import/Export buttons do nothing on click. Sort/filter state resets on navigating away and back.

**Sam (accessibility-dependent)**: The sitewide low-contrast focus indicator (P1 above) is the single most consequential gap — affects every form field in the panel. Notification bell and profile dropdowns (`AdminTopbar.tsx`) close only via mousedown-outside-listener, with no Escape key and no `aria-expanded`/`aria-haspopup` — notably, the mobile sidebar drawer *does* implement Escape-to-close, so the pattern exists in the codebase but wasn't reused here. The shared `Tooltip` component is hover-only with no `:focus-within` state, so a sighted keyboard user tabbing through icon-only Edit/Delete buttons never sees the label confirm what the button does (screen readers are unaffected — the `aria-label` is present independently). On the positive side: color is never used alone for status anywhere in the panel, and the `StockHealthDonut` chart's button-legend fallback is a genuine best-practice example.

## Minor Observations

- Notification Preferences (`settings/notifications/page.tsx`) holds its toggles in bare `useState` with no persistence and no save/feedback — different from the already-known, explicitly-marked password/2FA stubs; this one gives no indication either way that a change wasn't retained.
- The collapsed sidebar falls back to a native `title` tooltip for nav labels rather than the app's own `Tooltip` component used everywhere else — a small implementation inconsistency.
- `PagesTab.tsx`'s one non-editable row ("Best Sellers") renders identically to editable rows except the name isn't a link — easy to miss at a glance.
- `useAsyncAction.ts` simulates a fixed 700ms latency on every mock action — reasonable for demoing loading states today, but will feel sluggish to Alex once it's the *only* delay once real API calls land.

## Questions to Consider

- Should every content editor behave like Blog/Promotions (explicit draft → Save), or is instant-live editing actually the intended model for some sections and the "Discard" prompt is what's wrong?
- What would the highest-value first bulk action be — batch order-status update, or batch stock adjustment?
- Is Staff access truly single-tier in practice today, or does the RBAC gap need to close before more admins are added?

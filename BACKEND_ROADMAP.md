# Backend Build Roadmap — Cindyrella

A step-by-step guide to building the backend from scratch, by hand, for learning purposes.
Written 2026-09-25 from a full audit of `frontend/` (see the `// TODO` comments cited throughout —
grep for `TODO` in `frontend/` any time to re-check what's still stubbed).

## Starting point — read this first

There is currently **no backend**. Everything in `frontend/` runs on two separate in-memory mock
stores (`library/store.tsx` for the customer site, `library/adminStore.tsx` for admin) that reset
on every page reload and never talk to each other. Auth is fully faked: admin login accepts any
non-empty email/password (`library/adminStore.tsx:57`), and `frontend/proxy.ts` only checks that a
cookie *exists* (forgeable from devtools), not that it's valid.

The intended stack, already decided in `frontend/CLAUDE.md`:

- **API:** Node/Express, separate service from the Next.js app
- **DB:** PostgreSQL + Prisma
- **Payments:** PayMongo (GCash, Maya, cards)
- **Media:** Cloudinary
- **Auth:** JWT + httpOnly cookies, separate customer/admin roles

## How to use this guide

Work top to bottom — each phase unblocks the next one; don't skip ahead even if a later phase
looks more interesting. Each phase has:

- **Why this order** — the dependency reason it can't move later/earlier
- **Tasks** — what to actually build
- **Where the code goes** — exact file paths: what you create in `backend/`, and what existing
  `frontend/` file you edit to call it (replacing the mock logic there)
- **Done when** — a concrete check, not a vibe
- **Concepts you'll practice** — the specific skills this phase is *for*, since the point is
  upskilling, not just shipping

Don't build ahead of what the frontend currently needs. E.g. don't add multi-warehouse inventory
or subscription billing — none of that exists in the UI. Match backend scope to what's already
designed on the frontend.

## Phase 0 — Environment & project skeleton

**Why this order:** nothing else can start until there's a runnable API and a database to point it at.

**Tasks**

- [ ] Install PostgreSQL locally (or run it via Docker) and confirm you can connect with `psql`.

  ```powershell
  # Docker route (skip if you installed Postgres natively)
  docker run --name cindyrella-db -e POSTGRES_PASSWORD=devpassword -p 5432:5432 -d postgres:16
  psql -h localhost -U postgres
  ```

- [ ] Create `backend/` at the repo root, alongside `frontend/` — a separate service, not a
      Next.js API route (this is a deliberate architecture decision already made in `CLAUDE.md`,
      not a detail to reconsider).

  ```powershell
  New-Item -ItemType Directory -Path backend
  Set-Location backend
  npm init -y
  ```

- [ ] Install Express + TypeScript tooling:

  ```powershell
  npm install express cors dotenv
  npm install -D typescript tsx @types/node @types/express @types/cors
  npx tsc --init
  ```

- [ ] Set up `tsconfig.json`, a basic health-check route, and confirm it starts and responds. Add
      a `dev` script to `backend/package.json`: `"dev": "tsx watch src/index.ts"`, then run:

  ```powershell
  npm run dev
  ```

- [ ] Install Prisma (`prisma`, `@prisma/client`), run `npx prisma init`, point `DATABASE_URL` at
      your local Postgres in `.env`. **Do not commit `.env`** — add it to `.gitignore` now.

  ```powershell
  npm install @prisma/client
  npm install -D prisma
  npx prisma init
  ```

- [ ] CORS is already installed above (`cors` package) — wire it into `app.ts` so
      `localhost:3000` (the Next.js dev server) can call this API with credentials:

  ```ts
  app.use(cors({ origin: "http://localhost:3000", credentials: true }));
  ```

**Where the code goes**

- Backend — create: `backend/package.json`, `backend/tsconfig.json`, `backend/.env`,
  `backend/src/index.ts` (starts the server, imports `app.ts`), `backend/src/app.ts` (Express
  instance + CORS + JSON body parsing; route mounting comes in later phases).
- Backend — Prisma init creates `backend/prisma/schema.prisma` (still empty datasource block only).
- Frontend — create `frontend/.env.local` with `NEXT_PUBLIC_API_URL=http://localhost:<port>` (pick
  a port, e.g. 4000, distinct from Next's 3000). Nothing else on the frontend changes yet.

**Done when:** `curl localhost:<port>/health` returns `{ ok: true }` from a fresh `npm run dev`,
and `npx prisma studio` opens against an empty database.

**Concepts you'll practice:** Express app structure, environment config, connecting a Node process
to Postgres via Prisma's connection string.

## Phase 1 — Database schema

**Why this order:** every other phase writes to tables that need to exist first. Get this mostly
right now — retrofitting fields later (especially on `Product`) is exactly what `frontend/TODO.md`
warns against for `reorderThreshold` and per-size stock.

**Tasks** — model these in `schema.prisma`, in roughly this dependency order:

- [ ] `Customer` (id, email, passwordHash, name, createdAt) and `StaffMember` (id, email,
      passwordHash, name, `role` enum: `ADMINISTRATOR` | `STAFF`) — two separate tables, matching
      the two separate auth surfaces already designed.
- [ ] `Address` (belongs to `Customer`) — matches `app/account/addresses/page.tsx`.
- [ ] `Product` and `ProductSize` — **bake in `reorderThreshold` and per-size stock from day one**
      (explicitly flagged in `frontend/TODO.md` §3 as something that's worse to retrofit later).
      Look at `library/admin/products.ts`'s `AdminProduct` shape as your reference for fields —
      it's the more complete of the two existing frontend types.
- [ ] `StockMovement` (productId, sizeId nullable, quantity delta, reason enum, actor, timestamp) —
      the audit trail pattern already proven in the frontend's in-memory `stockLog`.
- [ ] `Order` and `OrderItem` — order needs a status field (history table comes in Phase 6).
- [ ] `Review` — matches `components/modals/ReviewModal.tsx`.
- [ ] `Voucher` — matches `app/account/vouchers/page.tsx`.
- [ ] CMS content tables (or a simpler JSON-blob-per-section table to start — see Phase 7 for why
      this one can be simple).
- [ ] Run the migration and confirm the tables exist in `psql` or Prisma Studio:

  ```powershell
  npx prisma migrate dev --name init
  npx prisma studio
  ```

**Where the code goes**

- Backend — edit: `backend/prisma/schema.prisma` (add every model above). Running the migrate
  command generates `backend/prisma/migrations/<timestamp>_init/`. No frontend files change.

**Done when:** `npx prisma studio` shows every table above with the right columns, and you can
manually insert one row into each via the Studio UI without a foreign-key error.

**Concepts you'll practice:** relational schema design, foreign keys, enums, when to normalize
(sizes, stock movements) vs. keep denormalized (a JSON content blob).

## Phase 2 — Auth (do this before any other endpoint)

**Why this order:** almost every other endpoint needs to know *who's* calling it before it can do
anything real (an order belongs to a customer, a product edit needs a role check). Building
product/order endpoints before auth means redoing them once auth exists.

**Tasks**

- [ ] Password hashing with `bcrypt` (or `argon2`), JWT signing with `jsonwebtoken`, and
      `cookie-parser` so Express can read the httpOnly cookie back on later requests:

  ```powershell
  npm install bcrypt jsonwebtoken cookie-parser
  npm install -D @types/bcrypt @types/jsonwebtoken @types/cookie-parser
  ```

- [ ] `POST /auth/customer/register`, `POST /auth/customer/login` — issue a signed JWT, set it as
      an **httpOnly** cookie (not returned in the response body — that's the whole point of
      httpOnly: JS on the page can't read it, which is what makes it safer than the current
      localStorage flag).
- [ ] `POST /auth/customer/otp/request` + `POST /auth/customer/otp/verify` — real one-time-code
      password reset.
- [ ] `POST /auth/admin/login` — same pattern, separate cookie name/table, checks `StaffMember`.
- [ ] `GET /auth/session` — returns the current user/staff from the verified cookie, or 401.
- [ ] Auth middleware: reads the JWT cookie, verifies the signature, attaches `req.user`
      (or `req.staff`) — reject with 401 if invalid/missing.
- [ ] RBAC middleware: `requireRole("ADMINISTRATOR")`, used on routes that should be
      admin-only (staff management, settings) vs. any-logged-in-staff. This is the fix for the
      RBAC gap flagged in `frontend/TODO.md`: `StaffMember.role` currently exists as a field but
      nothing checks it anywhere.

**Where the code goes**

- Backend — create: `backend/src/lib/prisma.ts`, `backend/src/lib/jwt.ts`,
  `backend/src/middleware/auth.ts`, `backend/src/middleware/rbac.ts`,
  `backend/src/controllers/auth.controller.ts`, `backend/src/routes/auth.routes.ts`.
- Backend — edit: `backend/src/app.ts` (mount `auth.routes.ts` at `/auth`).
- Frontend — create: `frontend/library/api/client.ts` (base `fetch` wrapper with
  `credentials: 'include'`), `frontend/library/api/auth.ts` (login/register/logout/session calls).
- Frontend — edit (replace the fake logic, call the new `api/auth.ts` functions):
  `components/modals/LoginModal.tsx` (lines 34, 40, 231, 243), `library/store.tsx:248`,
  `library/adminStore.tsx:57`.
- Frontend — edit `frontend/proxy.ts`: replace the "cookie exists" check with a real call to
  `GET /auth/session` (or verify the JWT signature directly at the edge) before gating `/admin/*`.

**Done when:** logging in via Postman/curl sets a real httpOnly JWT cookie you can inspect in
devtools (present, but its *value* isn't readable by `document.cookie`), an expired/tampered token
gets a 401, and a `STAFF`-role account gets a 403 on an admin-only route while `ADMINISTRATOR`
succeeds.

**Concepts you'll practice:** password hashing, JWT signing/verification, httpOnly cookies vs.
localStorage (and why that distinction is a real security boundary, not just a style choice),
middleware chains, role-based access control.

## Phase 3 — Products & the single-source-of-truth fix

**Why this order:** this is the biggest architectural gap in the current codebase — the customer
site and admin panel read two *independent* product datasets that never sync. Nothing about
inventory, cart, or checkout can be "real" until there's one place stock actually lives.

**Tasks**

- [ ] `GET /products`, `GET /products/:id` — public, no auth.
- [ ] `POST /products`, `PATCH /products/:id`, `DELETE /products/:id` — admin-only (RBAC-gated).
- [ ] Stock changes go through a **dedicated** endpoint/service function, not a raw `PATCH` field
      update — e.g. `POST /products/:id/stock-adjustment` with an explicit `reason` in the body
      (`"restock"`, `"correction"`, `"damaged"`, etc.), which also writes a `StockMovement` row.
      This directly fixes the diff-inference bug flagged in `frontend/TODO.md` §2, where
      `updateProduct` currently *guesses* in/out/adjustment by comparing old vs. new stock — a
      typo-only edit that happens to also touch stock gets miscategorized today.
- [ ] `GET /products/:id/stock-log` — paginated (see Phase 8 on why "paginated" isn't optional
      once this is real).
- [ ] CSV export (`GET /products/export.csv`) and CSV import (`POST /products/import`, bulk stock
      update) — validate rows server-side even though the frontend already validates client-side.
      For parsing/generating CSV and reading the uploaded file:

  ```powershell
  npm install csv-parse csv-stringify multer
  npm install -D @types/multer
  ```

**Where the code goes**

- Backend — create: `backend/src/controllers/products.controller.ts`,
  `backend/src/services/stock.service.ts`, `backend/src/routes/products.routes.ts`.
- Backend — edit: `backend/src/app.ts` (mount at `/products`).
- Frontend — create: `frontend/library/api/products.ts`.
- Frontend — edit: `library/store.tsx` (replace the static `PRODUCTS` import from
  `library/products.ts` with calls to `api/products.ts`), `library/adminStore.tsx` (replace
  `ADMIN_PRODUCTS`/`updateProduct`/`logStock` with API calls), `components/admin/modals/ProductModal.tsx`
  (submit handler calls create/update/stock-adjustment endpoints).
- Frontend — retire once migrated: `library/products.ts`, `library/admin/products.ts` (delete the
  static mock arrays — don't leave them as unused dead code).

**Done when:** editing stock in the admin panel and then loading the customer shop page shows the
updated number with **no frontend code change and no page-data hardcoding** — i.e. both sides are
now reading the same backend table. Try it manually: adjust stock via Prisma Studio directly and
confirm both `/shop` and `/admin/inventory` reflect it after a refetch.

**Concepts you'll practice:** REST resource design, separating "read" from "mutate with side
effects" (the stock-adjustment endpoint vs. a generic PATCH), designing an endpoint specifically to
prevent a class of bug (the reason-code fix).

## Phase 4 — Cart & atomic checkout

**Why this order:** depends on Phase 3 (real stock to check against) and Phase 2 (a customer to
attach the order to). This is where overselling becomes a real risk for the first time — mock data
never had concurrent users.

**Tasks**

- [ ] `POST /cart/check` (or inline into checkout) — server-side stock validation. Right now
      `addToCart` (`library/store.tsx:87`) only caps at a hardcoded `MAX_PER_ITEM = 6` — it never
      checks real availability. The frontend cart itself can stay client-state (localStorage/React
      state) for the *browsing* experience; it's checkout that must hit the server.
- [ ] `POST /orders` — creates the order **and** decrements stock **in the same database
      transaction** (`prisma.$transaction`). This is the concurrency-safety fix flagged explicitly
      in `frontend/TODO.md` §1's last bullet: two customers checking out the last unit at the same
      moment must not both succeed. Test this by hand — open two terminal tabs, fire two
      `POST /orders` for the same low-stock item back to back, and confirm only one succeeds.
- [ ] Decide and implement the cancellation/restock rule (does cancelling an order put stock back?
      — this is an open product decision from `frontend/TODO.md`, pick one and document it in a
      comment).
- [ ] `PATCH /orders/:id/status` (admin) — status transitions (history handled in Phase 6).

**Where the code goes**

- Backend — create: `backend/src/controllers/orders.controller.ts`,
  `backend/src/services/orders.service.ts` (the transaction logic lives here, not in the
  controller), `backend/src/routes/orders.routes.ts`.
- Backend — edit: `backend/src/app.ts` (mount at `/orders`).
- Frontend — create: `frontend/library/api/orders.ts`.
- Frontend — edit: `library/store.tsx:87` (`addToCart` calls the stock-check), `app/cart/page.tsx`
  (checkout submit calls `POST /orders`), `library/adminStore.tsx:174` (`updateOrderStatus` calls
  `PATCH /orders/:id/status`), `app/account/purchases/page.tsx:212` (real order actions).
- Frontend — retire once migrated: `library/orders.ts`, `library/admin/orders.ts`.

**Done when:** the double-checkout race test above only lets one request through when stock is 1,
and the loser gets a clear "out of stock" error, not a 500 or a silently oversold order.

**Concepts you'll practice:** database transactions, race conditions and how to actually reproduce
one locally, the difference between "the frontend prevents it" and "the database guarantees it."

## Phase 5 — Payments (PayMongo)

> **Superseded.** The shop has no PayMongo account: customers pay by transfer, upload a screenshot, and an admin verifies it. The PayMongo steps below were not used and the code was removed. See `BACKEND_PROGRESS.md` (Phase 5) for what was built instead.

**Why this order:** depends on Phase 4's order creation existing first — payment status updates an
order that must already exist.

**Tasks**

- [ ] Get PayMongo test-mode API keys, read their checkout-session or payment-intent docs. PayMongo
      has no official Node SDK — call its REST API directly with a plain HTTP client:

  ```powershell
  npm install axios
  ```

- [ ] `POST /orders/:id/payment-intent` — creates a PayMongo payment intent/checkout session for
      GCash/Maya/card, returns the client-facing redirect/token to the frontend cart page.
- [ ] Webhook endpoint (`POST /webhooks/paymongo`) — PayMongo calls this when payment succeeds or
      fails; **verify the webhook signature** (don't trust an unverified POST body to mark an order
      paid — this is a real fraud vector, not a hypothetical).
- [ ] On confirmed payment, transition the order to "Paid" and trigger whatever your Phase 4
      decision was for stock (if you chose "decrement on paid" rather than "decrement on order
      creation" — reconsider this now that payment is real, since "decrement on creation" risks
      holding stock hostage for abandoned/unpaid carts).

**Where the code goes**

- Backend — create: `backend/src/services/paymongo.service.ts`,
  `backend/src/controllers/payments.controller.ts`, `backend/src/routes/webhooks.routes.ts`.
- Backend — edit: `backend/src/app.ts` (mount webhook route at `/webhooks`; note this route needs
  the *raw* request body for signature verification, not the JSON-parsed one — configure that
  route's body parser separately from the rest of `app.ts`).
- Frontend — create: `frontend/library/api/payments.ts`.
- Frontend — edit: `app/cart/page.tsx` (payment step calls `POST /orders/:id/payment-intent` and
  redirects/embeds the PayMongo checkout).

**Done when:** a test-mode GCash/card payment in PayMongo's sandbox flips your order's status from
pending to paid via the webhook, without you manually updating anything.

**Concepts you'll practice:** third-party payment integration, webhook signature verification,
idempotency (a webhook can fire more than once — your handler must not double-process it).

## Phase 6 — Order/staff/content audit trails

**Why this order:** low risk, no hard dependency on anything after Phase 4 — but genuinely low
priority for a first working system, so it's deliberately placed after payments, not before.

**Tasks**

- [ ] `OrderStatusHistory` table — every status change appended, not overwritten.
      `GET /orders/:id/history` for the admin order detail view.
- [ ] Same pattern for staff account changes and CMS content edits — `frontend/TODO.md` flags all
      three (order status, staff, content) as currently having **zero** history, unlike inventory
      which already has a working pattern to copy (`StockMovement`).

**Where the code goes**

- Backend — edit: `backend/prisma/schema.prisma` (add `OrderStatusHistory`, `StaffAuditLog`,
  `ContentAuditLog` — or one generic `AuditLog` table with an `entityType` column, your call).
- Backend — create: `backend/src/services/audit.service.ts` (one `record()` function every
  controller calls after a mutation).
- Backend — edit: `backend/src/controllers/orders.controller.ts` (call `audit.service.ts` on every
  status change); staff and content controllers (created in later phases) call it too.
- Frontend — edit: admin order detail view (`components/admin/modals/OrderModal.tsx` or similar) to
  render the history list from `GET /orders/:id/history`.

**Done when:** changing an order's status twice in the admin panel shows both changes, with actor
and timestamp, in order.

**Concepts you'll practice:** append-only audit log design (never `UPDATE`, always `INSERT`).

**Why this order:** these are independent of the commerce core and don't block each other — pick

**Tasks**

      `library/admin/content.ts`'s in-memory state and previewed via admin's `useContent()`/live

- [ ] Cloudinary: server-side signed upload endpoint (`POST /uploads/signature`) so the frontend

## Phase 8 — Hardening & polish

**Why this order:** these only matter once the system is real and has real usage patterns; doing
them earlier is speculative work against data that doesn't exist yet.

**Tasks**

- [ ] Pagination everywhere a list can grow unbounded: stock log, order history, orders list,
      reviews. `frontend/TODO.md` explicitly flags the in-memory `stockLog` as unbounded — this is
      the same problem, for real.
- [ ] Optimistic concurrency on `Product` edits — a `version` or `updatedAt` check on write, so two
      admins editing the same product at once don't silently clobber each other. Flagged as
      irrelevant *today* (single-user mock) but real the moment there's more than one admin session.
- [ ] Rate limiting on auth endpoints (login, OTP request) — brute-force/spam protection.
- [ ] Input validation on every mutating endpoint (`zod` or similar) — don't trust client input,
      even from your own frontend.

  ```powershell
  npm install zod express-rate-limit
  ```

- [ ] Admin session list/revocation — now that sessions are real JWTs, list active ones per staff
      account and allow revoking.
- [ ] Admin 2FA (TOTP) — last on the list because it's an enhancement on top of already-working
      auth, not a blocker for anything else. `otplib` generates/verifies TOTP codes, `qrcode`
      renders the enrollment QR the admin scans in an authenticator app:

  ```powershell
  npm install otplib qrcode
  npm install -D @types/qrcode
  ```

**Where the code goes**

- Backend — create: `backend/src/middleware/rateLimit.ts`, `backend/src/middleware/validate.ts`
  (zod schemas, one per route file, e.g. co-located as `products.schema.ts` next to the
  controller), `backend/src/controllers/sessions.controller.ts` + `backend/src/routes/sessions.routes.ts`
  (list/revoke), TOTP logic added to `backend/src/controllers/auth.controller.ts`.
- Backend — edit: `backend/src/controllers/products.controller.ts` (add the `version` check on
  update), every `*.routes.ts` file (attach `rateLimit`/`validate` middleware where relevant).
- Frontend — edit: `app/admin/(panel)/settings/sessions/page.tsx` (call the new sessions endpoint),
  `app/admin/(panel)/settings/page.tsx:39` (real 2FA enrollment UI wired to the TOTP endpoints).

**Done when:** you can't think of an endpoint that trusts an unvalidated request body, a two-admin
edit race doesn't silently lose data, and no list endpoint can return 50,000 rows in one response.

**Concepts you'll practice:** the difference between "works in the demo" and "survives production,"
optimistic locking, input validation as a security boundary, rate limiting.

## Suggested milestones to actually check your progress
